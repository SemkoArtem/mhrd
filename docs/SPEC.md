# MHRD — специфікація RDP-клієнта

Oct 29, 2026 · @Артем

## Мета, принципи й стек

MHRD (MacroHard Remote Desktop, робоча назва) — легкий RDP-клієнт для Windows, Linux, macOS і Android: усі підключення й облікові записи в одному місці, вбудований WireGuard для доступу до ПК за білими списками, зашифрований бекап.

**Принципи**

- **Чиста кімната.** Функції описуємо за поведінкою застосунку Microsoft Remote Desktop, яку видно ззовні, і за відкритими специфікаціями протоколу RDP та формату `.rdp`. Код Microsoft не декомпілюємо й не використовуємо.
- **Легкість.** Мінімум налаштувань на головних екранах; рідкісні опції сховані в розділі «Додатково».
- **Один код інтерфейсу** для всіх платформ; різниця між ОС лише в нативних бібліотеках.
- **Без прав адміністратора.** Ні WireGuard, ні проксі не вимагають встановлення драйверів чи системного VPN.
- **Власна назва й оформлення.** Без назв, іконок і дизайну Microsoft; «WireGuard» лише в описі сумісності, не в назві.

**Стек**

| Шар | Технологія | Ліцензія |
| --- | --- | --- |
| Інтерфейс і логіка | Flutter (мова Dart) | BSD-3 |
| Протокол RDP | FreeRDP 3.x (C) | Apache 2.0 |
| WireGuard | wireguard-go, режим netstack (Go) | MIT |
| Сховище секретів | flutter\_secure\_storage | BSD-3 |
| Збірка | GitHub Actions (Windows, Linux, macOS) | — |

**Поза межами першої версії:** робочі простори RemoteApp/Azure Virtual Desktop, вхід через акаунт Microsoft, смарт-картки, USB-перенаправлення, принтери, камера.

**Не робимо взагалі:** iOS і власний сервер синхронізації. Між пристроями все переноситься зашифрованим файлом бекапу.

## Чим кращий за оригінал

Ми не копіюємо Microsoft Remote Desktop, а беремо його набір функцій за нижню планку. Кращими робимо три речі: стабільність, керування багатьма ПК і доступ через закриті мережі.

| Що | Оригінал | Наш застосунок |
| --- | --- | --- |
| Платформи | окремі застосунки з різними можливостями; немає Linux | один застосунок з однаковими функціями на Windows, Linux, macOS, Android |
| Акаунти | один на ПК | кілька на ПК, «Підключитись як…», одночасні сеанси різними акаунтами |
| Закриті мережі | лише RD Gateway або системний VPN | вбудований WireGuard, проксі — свій маршрут для кожного ПК, без прав адміністратора |
| Перенесення даних | залежно від версії, часто вручну | зашифрований бекап із паролями, автобекап, імпорт `.rdp` |
| Великі списки | плоскі групи | вкладені групи, теги, пошук, шаблони налаштувань, швидко на тисячах ПК |
| Діагностика | загальні коди помилок | етап, причина й порада простими словами, кнопка «Перевірити», Wake-on-LAN |

**Правила стабільності**

- Збій одного сеансу чи тунелю не зачіпає інші: кожен сеанс працює в **окремому процесі** `mhrd-session`; якщо FreeRDP упаде, закриється лише цей процес, а сеанс перейде в стан Failed із пропозицією перепідключитись.
- Інтерфейс ніколи не чекає на мережу: усі підключення й перевірки мають таймаут і кнопку «Скасувати».
- Запис даних атомарний: вимкнення світла під час збереження не пошкоджує список ПК.
- Перепідключення спершу піднімає тунель, потім сеанс: зміна Wi-Fi на мобільний інтернет не закриває сеанс.
- Кожна функція має тест у тест-плані, і збірка в GitHub Actions не проходить, якщо тести падають.

## Архітектура

Уся логіка й інтерфейс написані один раз на Flutter; під кожну ОС окремо збираються лише FreeRDP (у процесі `mhrd-session`), модулі тунелів і підключення до системного сховища.

Схема: Flutter (інтерфейс, дані й бекап, сеанси, маршрути, тунелі) ⇄ локальний канал + спільна пам'ять ⇄ процеси `mhrd-session` (по одному на сеанс, усередині FreeRDP). Шлях трафіку: FreeRDP у `mhrd-session` → 127.0.0.1:порт → тунель у застосунку → VPN-сервер → ПК:3389.

FreeRDP завжди підключається або напряму, або до локального порту 127.0.0.1, тому не знає, який саме тунель працює: новий тип VPN додається без змін у коді сеансу.

**Структура репозиторію**

```
mhrd/
├── lib/                    Dart: ui/, models/, storage/, sessions/, routes/
├── native/session/         C: процес mhrd-session над FreeRDP
├── native/host/            C++: плагін застосунку — запуск mhrd-session, канал, текстура з кадрів
├── native/tunnels/         Go: wireguard-go
├── third_party/FreeRDP/    вихідний код FreeRDP (git submodule)
├── windows/ linux/ macos/ android/   платформні проєкти Flutter
└── .github/workflows/      збірка під 4 ОС
```

**Сеанс в окремому процесі** (рішення власника, 30.10.2026). FreeRDP — код на C, і його збій (помилка пам'яті, зависання) у тому самому процесі закрив би весь застосунок з усіма сеансами. Тому кожен сеанс — окремий невеликий процес `mhrd-session`:

- **Керування й події** — через stdin/stdout процесу (анонімні канали: їх бачать лише застосунок і цей процес; однаково на Windows, Linux і macOS); на Android — служба в окремому процесі `:session`. Повідомлення — короткі бінарні кадри «довжина + тип + дані» (`native/session/src/proto.h`, `lib/sessions/session_protocol.dart`). Журнал FreeRDP іде в stderr.
- **Зображення** — через спільну пам'ять (file mapping на Windows, shm на Linux/macOS, SharedMemory на Android): `mhrd-session` пише змінені ділянки кадру, плагін застосунку (`native/host`) копіює їх у текстуру Flutter. Через канал іде лише «ділянка x, y, w, h оновилась».
- **Паролі** передаються в `mhrd-session` лише через канал під час старту — ніколи в аргументах командного рядка чи змінних середовища, які бачать інші програми.
- **Тунелі** лишаються в процесі застосунку: `mhrd-session` підключається або напряму, або до `127.0.0.1:<порт>`.
- **Нагляд:** якщо процес завершився без події `disconnected`, це збій — стан Failed і пропозиція перепідключитись. «Відключитись» спершу просить процес завершитись сам, а через 5 с закриває його примусово.

Повідомлення каналу:

```
застосунок -> mhrd-session:
connect(config, password)          # одразу після запуску процесу
key(scancode, pressed)
mouse(x, y, buttons, wheel)
resize(width, height)
clipboard(format, data)
reconnect / disconnect

mhrd-session -> застосунок:
frame(x, y, w, h)                  # пікселі BGRA — у спільній пам'яті
resized(w, h)                      # нова спільна пам'ять під новий розмір
certificate(fingerprint, subject), authFailed, connected, disconnected(reason), clipboard(formats)
```

Повільний сервер чи збій одного сеансу не гальмує інтерфейс та інші сеанси: це різні процеси.

## Модель даних

Облікові записи, шлюзи, профілі WireGuard і проксі зберігаються окремими списками, а підключення лише посилається на них за id. Один акаунт чи тунель може обслуговувати багато підключень, і зміна пароля робиться в одному місці. Секрети (паролі, ключі) ніколи не лежать у файлі даних: там лише ключ `secretRef` до системного сховища.

**Підключення (Connection)**

| Поле | Тип | Примітка |
| --- | --- | --- |
| id | UUID |  |
| name, group, tags | текст | група = папка в списку, теги для пошуку |
| host, port | текст, число | порт за замовчуванням 3389 |
| credentialIds | список id | кілька акаунтів на один ПК; перший = за замовчуванням |
| route | перелік | direct / tunnel / proxy |
| routeRefId | id | профіль тунелю WireGuard або проксі |
| gatewayId | id або порожньо | RD Gateway |
| display | об'єкт | монітори, роздільна здатність, масштаб, режим зміни розміру |
| devices | об'єкт | буфер, диски, звук, мікрофон |
| adminSession | так/ні | підключення до консольного сеансу |
| certPin | текст | відбиток сертифіката сервера, який користувач підтвердив |
| wakeOnLan | об'єкт | MAC-адреса, broadcast-адреса |
| lastUsed, thumbnail | дата, файл | для сортування й плиток |

**Ще два поля ПК з документації оригіналу:** swapMouseButtons (ліва й права кнопки міняються місцями, для лівшів) і displayScale (збільшення елементів на віддаленому ПК при високій роздільній здатності, 100–300 %).

**Адреса в одному полі.** Як і в оригіналі, користувач може ввести `MyDesktop:3390` або `10.0.0.1:3390`. Під час збереження адреса розбивається на host і port; IPv6 — у квадратних дужках, `[fd00::5]:3389`. Назва необов'язкова: якщо порожня, показується адреса.

**Поля з вікна «Додати ПК» у клієнті для macOS** (підтверджено скриншотом вкладки General у статті DePaul KB0011601; типово: «Перепідключатися» увімкнено, решта вимкнено):

| Поле | Тип | У MHRD |
| --- | --- | --- |
| reconnectOnDrop | так/ні | типово «так»; вимикає автоперепідключення для цього ПК |
| gatewayBypassLocal | так/ні | не йти через RD Gateway, коли ПК у локальній мережі (приватна адреса або ім'я розв'язується локально) |
| display.startFullscreen | так/ні/за загальним | перевизначає глобальне налаштування |
| display.useAllMonitors | так/ні | див. «Кілька моніторів» |
| display.colorDepth | 15 / 16 / 24 / 32 біти | типово 32; менше — менше трафіку на повільних каналах |
| display.hiDpi | так/ні | повна роздільна здатність Retina та HiDPI-екранів будь-якої ОС; попередження про приблизно четверо більший трафік |
| folders | список {назва, шлях, лише читання} | див. «Перенаправлення пристроїв» |

Режими зміни розміру «Підлаштувати під вікно» і «Оновлювати роздільність при зміні розміру» відповідають нашим режимам «Масштабувати» і «Змінювати роздільність». Стандартна група для ПК без групи називається «Збережені ПК».

**Обліковий запис (Credential):** id, назва, користувач (`DOMAIN\user` або `user@domain`), `secretRef` до пароля.

Режим входу облікового запису: збережений пароль або запит пароля при кожному підключенні. ПК можна зберегти без пароля й без доступного сервера. Зміна пароля в акаунті одразу діє для всіх ПК, які на нього посилаються.

**Група (Group):** id, назва, parentGroupId (вкладені групи із захистом від циклів), порядок сортування. Видалення групи питає, куди перенести її ПК.

**Профіль екрана (DisplayProfile) і профіль пристроїв (RedirectionProfile):** окремі шаблони налаштувань, які можна призначити багатьом ПК, наприклад «Офіс, 2 монітори» чи «Телефон, без дисків». ПК або посилається на шаблон, або має власні значення.

**Видалення пов'язаних об'єктів:** якщо акаунт, шлюз чи тунель використовують якісь ПК, застосунок показує їх список і питає підтвердження. ПК з поламаним посиланням позначається попередженням, а не падає при запуску.

**Шлюз (Gateway):** id, назва, адреса, порт, credentialId або «той самий акаунт, що й для ПК».

Шлюзи часто вимагають другий фактор (Duo тощо): вхід чекає на підтвердження в телефоні. Тому таймаут автентифікації шлюзу — 90 с, а статус сеансу — «Шлюз чекає на підтвердження входу…». Автоперепідключення через шлюз використовує cookie сеансу, щоб не запитувати другий фактор щоразу, коли це дозволяє сервер.

На macOS дозволи на мікрофон і камеру діють лише після перезапуску застосунку: MHRD виявляє, що дозвіл надано, і пропонує перезапуск зі збереженням відкритих сеансів у списку для швидкого повернення.

**Профіль WireGuard (WgProfile)**

| Поле | Тип | Примітка |
| --- | --- | --- |
| id, name |  |  |
| privateKey | `secretRef` | у системному сховищі |
| addresses | список CIDR | адреса в тунелі, наприклад 10.8.0.2/32 |
| dns | список IP | для імен хостів всередині тунелю |
| mtu | число | за замовчуванням 1420 |
| peer.publicKey | текст |  |
| peer.presharedKey | `secretRef` | необов'язково |
| peer.endpoint | host:port |  |
| peer.allowedIps | список CIDR |  |
| peer.keepalive | секунди | рекомендовано 25 за NAT |

**Проксі (ProxyProfile):** id, назва, тип (SOCKS5 / HTTP), адреса, порт, логін і `secretRef`.

**Загальні налаштування (AppSettings):** тема, мова, вигляд списку (плитки / рядки), новий сеанс у вкладці чи вікні, повний екран при старті, не вимикати екран під час сеансу, блокування застосунку PIN-кодом чи біометрією.

Усе, крім секретів, зберігається у локальній базі SQLite у теці даних застосунку (швидко навіть на тисячах ПК) з полем `schemaVersion` для міграцій між версіями.

## Екрани й інтерфейс

Застосунок має чотири основні екрани: список, редагування, сеанс і налаштування. На широкому екрані список і редагування стоять поруч, на телефоні відкриваються один за одним.

**1. Головний екран**

- Вкладки: «ПК», «Акаунти», «Маршрути» (тунелі, проксі, шлюзи).
- ПК показані плитками з мініатюрою останнього сеансу або компактними рядками, згруповані за папками.
- Пошук за назвою, адресою, групою, тегом; сортування за назвою або останнім використанням.
- На плитці: назва, адреса, значок маршруту (замок = тунель), статус «підключено», якщо сеанс відкритий.
- Клік = підключитись акаунтом за замовчуванням. Правий клік / довге натискання = меню: «Підключитись як…» (вибір акаунта), «Редагувати», «Дублювати», «Експортувати .rdp», «Перемістити в групу», «Розбудити (Wake-on-LAN)», «Видалити».
- Кнопка «+»: новий ПК, акаунт, маршрут, імпорт `.rdp`, імпорт конфігурації VPN.

**2. Редагування ПК**

- Видимі одразу: назва, адреса, акаунти (список з перетягуванням, перший = за замовчуванням), маршрут, папка.
- Розгортані блоки: «Екран», «Пристрої», «Додатково» (шлюз, порт, адміністративний сеанс, Wake-on-LAN, теги).
- Кнопка «Перевірити»: відкриває маршрут і перевіряє, чи відповідає порт RDP, без повного підключення.

**3. Сеанс**

- Кілька сеансів одночасно: вкладки на десктопі, бічна панель з мініатюрами на Android; за налаштуванням кожен сеанс у власному вікні.
- Верхня панель, що ховається: назва ПК, маршрут, якість з'єднання (затримка), повний екран, масштаб, Ctrl+Alt+Del, відключитись.
- Android: екранна клавіатура, рядок спецклавіш (Esc, Tab, Ctrl, Alt, Win, F1–F12, стрілки), перемикач «дотик / миша».
- Під час втрати зв'язку — напівпрозорий шар «Перепідключення… спроба 2 з 5» з кнопкою «Скасувати».

**4. Налаштування**

- Тема, мова, вигляд списку, поведінка сеансів (вкладка чи вікно), блокування PIN-кодом.
- Бекап: експорт, імпорт, дата останнього бекапу, автобекап у вибрану папку.
- Діагностика: журнал підключень (без паролів), кнопка «Скопіювати журнал».

**Що підтверджує документація Microsoft і як це робить MHRD**

| Функція оригіналу | Де була | У MHRD |
| --- | --- | --- |
| «Питати щоразу» замість збереженого акаунта | Windows, Android | так, режим входу акаунта або ПК без акаунта |
| Шлюз з опцією «використовувати акаунт ПК» | усі | так |
| Закріпити ПК у меню «Пуск» / віджет на головному екрані | Windows / Android | ярлик на робочому столі (усі десктопи), віджет і ярлики (Android); перейменування ПК оновлює підпис — в оригіналі не оновлювалося |
| Експорт і імпорт `.rdp` окремого ПК | macOS | усі платформи, також масовий імпорт папки з `.rdp` |
| Список своїх роздільних здатностей (додати / видалити) | macOS | так, у шаблонах екрана |
| Глобальна роздільна здатність + перевизначення для ПК | Android | так: шаблон за замовчуванням + власні значення ПК |
| Запускати на весь екран; кожен сеанс у новому вікні | Windows | так |
| За зміни розміру вікна: розтягнути зі збереженням пропорцій (типово) | Windows | три режими (див. «Зміна розміру вікна»), типово — зміна роздільності |
| Куди йдуть Win і Alt+Tab: лише в повному екрані (типово) / завжди / ніколи | Windows | так, ті самі три варіанти |
| Не вимикати екран під час сеансу | Windows | так |
| Попередній перегляд ПК у списку | Windows, Android | так, мініатюра останнього сеансу, вимикається |
| Анонімна телеметрія (увімкнена за замовчуванням) | Windows, Android | немає взагалі |
| Видалення кількох акаунтів чи шлюзів довгим натисканням | Android | множинний вибір для усіх списків, включно з ПК |
| Робочі простори / RemoteApp-фіди | усі | не в першій версії |

**Панелі сеансу на сенсорних пристроях.** Панель підключення зверху можна перетягувати ліворуч і праворуч. Зліва відкривається список сеансів (перемикання, «Новий сеанс», × для відключення), справа — команди: «До списку», «Відключитись», «Повний екран», «Дотик / Миша». Повернення до списку не розриває сеанс, а «Відключитись» залишає програми на ПК запущеними. У нас це додається до верхньої панелі, описаної вище.

**Швидке підключення.** Як «PC Quick Connect» у клієнті для macOS: поле адреси вгорі головного екрана (Ctrl/⌘+K) для разового підключення без створення ПК. Після сеансу MHRD пропонує «Зберегти цей ПК» з уже введеними даними — цього в оригіналі не було.

**Діалог облікових даних** (коли акаунт = «Питати щоразу»): заголовок, явний перелік, для чого буде використано дані («ПК 140.192.x.x і шлюз rdgateway…»), поля «Користувач» і «Пароль», прапорець «Показати пароль». Понад оригінал: прапорець «Зберегти як обліковий запис» і підказка формату (`DOMAIN\user` або `user@domain`).

**Структура налаштувань на десктопі:** вкладки «Загальні», «Облікові записи», «Маршрути» (шлюзи, тунелі, проксі), «Групи», «Шаблони екрана», «Бекап». У кожному списку — кнопки «+» і «−».

**Гарячі клавіші головного вікна** (Ctrl на Windows/Linux, ⌘ на macOS): N — додати ПК, K — швидке підключення, F — пошук, «,» — налаштування, Enter — підключитись до вибраного, Delete — видалити з підтвердженням. Імпорт у меню «Файл»: з `.rdp`-файлів і з бекапу MHRD.

## Теми й оформлення

Типова тема MHRD — «Графіт» (варіант A): графітовий фон, лаймовий акцент, IBM Plex Sans для тексту й IBM Plex Mono для адрес. Усі кольори й розміри в коді беруться з токенів теми, тому користувач може змінити вигляд цілком, не чіпаючи розмітку.

**Вбудовані теми:** «Графіт» (типова), «Світлий інструмент» (варіант B), «Нічний бурштин» (варіант C), а також «Як у системі» — автоматичне перемикання між світлою й темною за налаштуванням ОС.

**Токени теми** (те, що користувач може змінити)

| Група | Токени |
| --- | --- |
| Кольори | фон, поверхня, рамка, текст, другорядний текст, акцент, текст на акценті, статуси (підключено, перепідключення, помилка) |
| Шрифти | основний, моноширинний, базовий розмір (90–130 %) |
| Форма | радіус кутів (0–20 px), щільність (компактно / звичайно / просторо) |
| Рух | анімації: повні / лише необхідні / вимкнено (типово відповідає системному «зменшити рух») |
| Список ПК | типовий вигляд (плитки / список), показ мініатюр |

**Редактор теми** у налаштуваннях: вибрати основу з вбудованих, змінити будь-які токени з живим попереднім переглядом, зберегти під власною назвою. Редактор перевіряє контраст тексту (не менше 4,5 : 1) і попереджає, коли текст стає погано читабельним. Кнопка «Скинути» повертає типові значення.

**Обмін темами:** експорт і імпорт теми окремим файлом `.mhrd-theme` (JSON з `schemaVersion`), тож темами можна ділитися. Власні теми входять у повний бекап. Імпортована тема містить лише значення токенів (кольори, числа, назви шрифтів із вбудованого набору), жодного коду чи посилань, і перевіряється перед застосуванням.

## Підключення й сеанс

Підключення проходить шість кроків: маршрут → перевірка порту → TLS і сертифікат → вхід (NLA) → сеанс → прибирання. Кожен крок має свій текст помилки, щоб користувач бачив, де саме зупинилось.

**Стани сесії**

| Стан | Що показує інтерфейс |
| --- | --- |
| Resolving | «Пошук адреси…» |
| Tunneling | «Підключення тунелю <назва>…» (лише для маршрутів через тунель) |
| Connecting | «З'єднання з ПК…» |
| Negotiating | «Перевірка сертифіката…» |
| Authenticating | «Вхід як <акаунт>…» |
| Connected | картинка сеансу, тривалість у панелі |
| Reconnecting | шар «Перепідключення… спроба N з 5» |
| Disconnected | причина відключення, кнопка «Підключитись знову» |
| Failed | етап, на якому зупинилось, причина, порада, кнопка «Деталі» |

Стан сесії ніколи не змінює збережених налаштувань ПК, а збій одного сеансу не впливає на інші.

**Підключення**

```
function connect(pc, credential = pc.credentials.first):
    session = new Session(pc)
    show(session, status = "Підключення…")

    # 1. маршрут: куди насправді стукає FreeRDP
    target = routes.open(pc.route, pc.routeRefId, pc.host, pc.port)
        # direct  -> (pc.host, pc.port)
        # tunnel  -> ("127.0.0.1", локальний_порт)  див. «Вбудовані тунелі»
        # proxy   -> FreeRDP сам іде через проксі
    on error: fail(session, "Не вдалося відкрити маршрут: " + причина)

    # 2. швидка перевірка, що порт відповідає (таймаут 5 с)
    if not tcpReachable(target, timeout = 5s):
        if pc.wakeOnLan: offer("ПК не відповідає. Розбудити?")
        fail(session, "ПК недоступний")

    # 3. параметри FreeRDP
    cfg = FreeRdpConfig(
        host = target.host, port = target.port,
        serverName = pc.host,                 # для сертифіката й Kerberos, не 127.0.0.1
        user = credential.user, domain = credential.domain,
        password = secrets.read(credential.secretRef),
        gateway = pc.gateway, proxy = pc.proxyIfAny,
        width, height = display.initialSize(pc),
        monitors = pc.display.monitors,
        devices = pc.devices,
        admin = pc.adminSession)

    # 4. запуск; далі все приходить подіями з нативного шару
    native.start(session.id, cfg)
    wipe(cfg.password)
```

**Події від нативного шару**

| Подія | Що робить застосунок |
| --- | --- |
| certificate(fingerprint, subject) | збігається з `certPin` → продовжити; новий або змінений → діалог «Довіряти?», при згоді зберегти `certPin` |
| authFailed | показати «Невірний логін або пароль», запропонувати інший акаунт |
| connected | статус «Підключено», `lastUsed = now` |
| frame(x, y, w, h) | оновити ділянку зображення на екрані |
| resized(w, h) | сервер змінив роздільність, перебудувати полотно |
| clipboard(formats) | див. «Перенаправлення» |
| disconnected(reason) | якщо причина мережева → перепідключення, інакше закрити сеанс з поясненням |

**Перепідключення**

```
function onDisconnected(session, reason):
    if reason in [ВИХІД_КОРИСТУВАЧА, ВИХІД_НА_СЕРВЕРІ, ВХІД_З_ІНШОГО_МІСЦЯ]:
        close(session, message(reason)); return

    for attempt in 1..5:
        show(session, "Перепідключення… спроба " + attempt + " з 5")
        wait(min(2^attempt, 30) seconds)        # 2, 4, 8, 16, 30 с
        if session.cancelled: return
        routes.ensureAlive(session.route)       # тунель міг упасти разом з мережею
        if native.reconnect(session.id): return # FreeRDP використовує auto-reconnect cookie
    close(session, "З'єднання втрачено")
```

**Зміна розміру вікна**

- Режим «Змінювати роздільність» (за замовчуванням): після того як користувач перестав тягнути вікно 300 мс, надіслати нову роздільність через канал Display Control. Якщо сервер його не підтримує, перейти в режим масштабування.
- Режим «Масштабувати»: роздільність не змінюється, картинка масштабується зі збереженням пропорцій.
- Режим «Без змін»: картинка 1:1 зі смугами прокрутки.

**Кілька моніторів** (десктопи)

| Ситуація | Поведінка MHRD |
| --- | --- |
| Один монітор | сеанс у вікні або на весь екран цього монітора |
| «Усі монітори» | сервер отримує список моніторів з їхніми позиціями й роздільними здатностями; у Windows на віддаленому ПК видно стільки ж екранів |
| Вибрані монітори | понад оригінал: вибір конкретних моніторів за схемою їх розташування |
| Різні масштаби екранів (наприклад, 4K + Full HD) | кожен монітор передає свій масштаб, щоб текст не був дрібним чи розмитим |
| Підключення або від'єднання монітора під час сеансу | новий набір моніторів передається через Display Control без перепідключення, якщо сервер підтримує |
| macOS, «Монітори мають окремі Spaces» вимкнено | інакше повноекранний сеанс на одному моніторі залишає інші порожніми: MHRD виявляє це налаштування, у такому разі відкриває сеанс у вікні на весь монітор і показує підказку |
| macOS + iPad через Sidecar | iPad вважається звичайним монітором і може бути вибраний для сеансу |
| Retina / HiDPI | типово сеанс у логічній роздільній здатності; «hiDpi» вмикає фізичну з масштабом 200 % на сервері |

**Ввід**

- Клавіатура передається скан-кодами, а не символами, тому працює будь-яка розкладка віддаленого ПК. Поєднання Win, Alt+Tab, Ctrl+Esc у повноекранному режимі перехоплюються й ідуть на віддалений ПК.
- Миша: абсолютні координати, коліщатко, ліва/права/середня кнопки.
- Android, режим «дотик»: дотик = клік, утримання = правий клік, два пальці = прокрутка, щипок = масштаб. Режим «миша»: палець рухає курсор, як тачпад.

**Жести на сенсорному екрані** (збігаються з оригіналом, щоб не перевчати користувачів)

| Режим | Дія | Жест |
| --- | --- | --- |
| Дотик | лівий клік | дотик одним пальцем |
| Дотик | правий клік | утримання одним пальцем |
| Дотик | перегляд збільшеного екрана | елемент панорамування: утримати й тягнути |
| Миша | лівий клік | дотик одним пальцем |
| Миша | перетягування лівою | подвійний дотик із утриманням, потім рух |
| Миша | правий клік | дотик двома пальцями |
| Миша | перетягування правою | подвійний дотик двома пальцями із утриманням, потім рух |
| Миша | коліщатко | утримання двома пальцями, потім вгору чи вниз |
| Миша | масштаб | зведення або розведення двох пальців |

Налаштування вводу: «Масштаб щипком» (вимкнути, коли віддалена програма сама обробляє багатоточковий дотик) і «Надсилати скан-коди» (типово; вимкнення перемикає на Unicode для програм, які неправильно приймають клавіші з екранної клавіатури).

**Клавіатура macOS** (типове відображення, як в оригіналі): Cmd → Win; поєднання Cmd+C/V/X/Z/A → Ctrl+…; F1–F12 через Fn; правий Option → AltGr. У MHRD це налаштовується.

**Прострочений пароль.** Якщо сервер повідомляє, що пароль прострочений, застосунок пропонує ввести новий і оновлює його в акаунті (для всіх ПК, що на нього посилаються), а не просто показує код помилки.

## Вбудований тунель: WireGuard

Усі VPN-тунелі працюють усередині застосунку зі своїм мережевим стеком, без системного VPN і без прав адміністратора. Через тунель іде лише трафік RDP; інший VPN на пристрої не зачіпається, і кілька тунелів можуть працювати одночасно.

**Типи тунелів**

| Тип | Бібліотека | Ліцензія | Як працює без прав адміністратора | Складність | Версія |
| --- | --- | --- | --- | --- | --- |
| WireGuard | wireguard-go (Go) | MIT | вбудований режим netstack | низька | 1 |

Tailscale/Headscale, OpenVPN, OpenConnect (Cisco AnyConnect, Fortinet, GlobalProtect, Pulse), IPsec/IKEv2 і L2TP не вбудовуємо (рішення власника, 2026-10-31). Для них і будь-яких інших VPN діє маршрут «напряму» поверх системного VPN, уже ввімкненого користувачем.

**Спільний інтерфейс тунелю**

```
interface Tunnel:
    start(profile)              # підняти тунель, чекати рукостискання (таймаут 15 с)
    dial(host, port) -> stream  # TCP-з'єднання ЧЕРЕЗ тунель
    resolve(name) -> ip         # DNS-запит через DNS тунелю
    stop()
    state                       # connecting / up / error(причина)
    lastHandshake, rx, tx       # для діагностики
```

Кожен тип із таблиці реалізує цей інтерфейс у нативному модулі. Решта застосунку не знає, який саме VPN працює.

**Менеджер тунелів і переадресація портів**

```
class TunnelManager:
    active = {}                 # profileId -> (tunnel, лічильник користувачів)

    function open(profileId, host, port) -> localPort:
        if profileId not in active:
            tunnel = createTunnel(profiles[profileId].type)
            tunnel.start(profiles[profileId])     # помилка -> «Тунель не піднявся: …»
            active[profileId] = (tunnel, 0)
        active[profileId].users += 1

        ip = isIp(host) ? host : tunnel.resolve(host)
        listener = listen("127.0.0.1", port = 0)  # випадковий вільний порт, лише localhost
        on listener.accept(client):
            remote = tunnel.dial(ip, port)
            pipe(client <-> remote)               # два потоки копіювання байтів
        return listener.port

    function release(profileId):
        active[profileId].users -= 1
        if users == 0: after 60 s with no new users -> tunnel.stop(); remove
```

Тунель живе ще 60 с після останнього сеансу, щоб перепідключення або другий сеанс через той самий профіль не чекали нового рукостискання.

**Профілі й імпорт**

- Кілька профілів будь-якого типу; кожен ПК посилається на один.
- WireGuard: імпорт `.conf`, QR-код на Android, ручне введення, генерація пари ключів з показом публічного ключа для сервера.
- Ключі, сертифікати й паролі лежать у системному сховищі та входять у зашифрований бекап.

**Білі списки.** Віддалений ПК бачить адресу, з якої трафік виходить з VPN-сервера, тому ця адреса має бути постійною: власний сервер чи роутер або виділена IP-адреса у провайдера. Спільні сервери комерційних VPN для білих списків не годяться.

## Інші маршрути: проксі, RD Gateway

Проксі й RD Gateway FreeRDP підтримує сам, тому застосунок лише передає йому параметри.

| Маршрут | Реалізація | Коли потрібний |
| --- | --- | --- |
| SOCKS5 або HTTP-проксі | параметр проксі FreeRDP, з логіном і паролем | корпоративна мережа з проксі, проксі з постійною IP для білого списку |
| RD Gateway | параметр gateway FreeRDP (транспорт HTTP/WebSocket, RPC як резерв) | корпоративний шлюз Microsoft на порту 443 |

SSH-тунель не вбудовуємо (рішення власника, 2026-10-31). ПК зі старим маршрутом SSH (база чи бекап) отримують «тунель без профілю»: підключення дає зрозумілу помилку, а не йде напряму.

**Ланцюжки маршрутів.** У першій версії один ПК = один маршрут. RD Gateway можна поєднати з будь-яким із тунелів (шлюз стає ціллю тунелю). Інші комбінації — після першої версії, якщо з'явиться потреба.

## Безпека, бекап і відновлення

Секрети зберігаються тільки в системному сховищі ОС, а за його межі виходять лише в бекапі, зашифрованому паролем користувача.

**Сховище секретів**

| Платформа | Де лежать паролі й ключі |
| --- | --- |
| Windows | Credential Manager / DPAPI |
| macOS | Keychain |
| Linux | Secret Service (libsecret: GNOME Keyring, KWallet) |
| Android | Keystore + зашифровані налаштування |

Якщо на Linux немає Secret Service (мінімальні системи без стільниці), застосунок пропонує головний пароль і шифрує секрети сам, тим самим алгоритмом, що й бекап.

**Інші правила**

- Сертифікат RDP-сервера підтверджується при першому підключенні й запам'ятовується. Зміна сертифіката = червоне попередження, а не тиха згода.
- NLA (CredSSP) увімкнена за замовчуванням. Вимкнути можна лише в «Додатково» з попередженням.
- Журнал не містить паролів, ключів і вмісту буфера обміну.
- Блокування застосунку PIN-кодом або біометрією — за бажанням, після N хвилин неактивності.
- На Android екран сеансу позначений як захищений від знімків у списку недавніх застосунків.

**Формат бекапу**

```
файл .rdpbackup =
    "RDPB2"                      # підпис формату, версія 2
    kdf = Argon2id(пам'ять 64 МБ, ітерацій 3, потоків 1)
    salt (16 байтів), nonce (12 байтів)
    AES-256-GCM( JSON { schemaVersion, підключення, акаунти + паролі,
                        шлюзи, профілі тунелів + ключі, проксі,
                        налаштування } )
    # заголовок входить у перевірку цілісності (AAD)
```

Імпорт також читає бекапи першої Windows-версії (формат «RDPB1», PBKDF2), щоб нічого не вводити заново.

**Відновлення**

```
function importBackup(file, password, mode):   # mode = «об'єднати» | «замінити все»
    data = decrypt(file, password)
        on auth-tag error: fail("Невірний пароль або файл пошкоджено")
    data = migrate(data, from = data.schemaVersion)
    preview("Буде додано N, оновлено M, видалено K")  -> користувач підтверджує
    if mode == замінити: exportBackup(автоматично, поточний стан)  # страховка
    for each item: той самий id -> замінити, новий -> додати
    секрети -> системне сховище; решта -> файл даних
```

Автобекап: за бажанням, у вибрану папку (наприклад, синхронізовану з хмарою) після кожної зміни, не частіше разу на годину, зберігаються останні 10 копій. Пароль автобекапу зберігається в системному сховищі.

**Два види експорту**

|  | Повний бекап | Експорт для передачі |
| --- | --- | --- |
| Для чого | перенести все на інший свій пристрій | поділитися списком ПК з колегою |
| Секрети | так, зашифровані паролем бекапу | ніколи |
| Що вибрати | усе | вибрані ПК або групи |
| Формат | `.rdpbackup` (зашифрований) | `.json` з `schemaVersion` і `secretIncluded: false` |

## Перенаправлення пристроїв

Усе перенаправлення йде стандартними віртуальними каналами RDP, які вже є у FreeRDP. Застосунок відповідає лише за зв'язок із системою (буфер обміну, вибір папки, дозвіл на мікрофон).

| Функція | Канал RDP | За замовчуванням | Примітка |
| --- | --- | --- | --- |
| Буфер обміну: текст, зображення | cliprdr | увімкнено | версія 1; файли через буфер — пізніше |
| Локальні папки | rdpdr (диски) | вимкнено | список папок: назва в сеансі, шлях, «лише читання»; кожна з'являється як мережевий диск у «Цей ПК». Режим доступу: **«додавати без видалення»** (типовий: читати все, класти нове, працювати зі створеним у цьому сеансі; не видаляти, не перейменовувати, не змінювати наявне), «повний», «лише читання». FreeRDP цих режимів не має — їх виконує наш доповнений канал drive (`native/session/vcpkg-overlay/freerdp/mhrd/drive_main.c`, блоки «MHRD:») |
| Звук з віддаленого ПК | rdpsnd | тут | варіанти: тут / на віддаленому ПК / вимкнено |
| Мікрофон | audin | вимкнено | запит дозволу ОС при першому ввімкненні |
| Кілька моніторів | монітори в параметрах підключення | один | лише десктоп; вибір конкретних моніторів |
| Зміна роздільності | disp (Display Control) | увімкнено | див. «Підключення й сеанс» |
| Принтери, смарт-картки, камера (є в клієнті для macOS), USB | — | — | після першої версії; принтери й смарт-картки FreeRDP уже підтримує, тож вони перші в черзі |

**Буфер обміну**

```
локальний буфер змінився (фокус на вікні сеансу або перевірка раз на секунду):
    native.clipboardAnnounce(session, доступні_формати)   # дані ще не надсилаємо
server запитує формат:
    native.clipboardSend(session, дані_в_цьому_форматі)   # лише коли на ПК натиснули «Вставити»
server оголосив новий вміст:
    запитати текст (Unicode) або зображення -> покласти в локальний буфер
```

Кожен ресурс вмикається лише тоді, коли його дозволяють усі три рівні: підтримка застосунку на цій ОС, налаштування ПК і політика сервера. Якщо сервер забороняє необов'язковий ресурс (диски, звук), сеанс відкривається без нього з повідомленням, а не падає.

## Помилки й діагностика

Кожна помилка показує три речі: на якому етапі зупинилось, причину простими словами і що зробити. Технічний код доступний під кнопкою «Деталі».

| Категорія | Приклад | Реакція застосунку |
| --- | --- | --- |
| Тунель | немає рукостискання WireGuard за 15 с | назва тунелю й етап; порада перевірити ключі, endpoint, час на пристрої |
| DNS і мережа | адресу не знайдено, немає інтернету | адреса й етап; порада перевірити мережу чи DNS тунелю |
| Порт і фаєрвол | 3389 не відповідає | адреса й порт; пропозиція Wake-on-LAN, якщо налаштований |
| Сертифікат | новий, змінений, прострочений | деталі сертифіката; змінений — червоне попередження, жодного тихого обходу |
| Вхід | невірний пароль, NLA відхилена, акаунт заблокований | без автоматичних повторів (щоб не заблокувати акаунт); пропозиція ввести пароль чи вибрати інший акаунт |
| RD Gateway | шлюз недоступний або відхилив вхід | чітко відрізняти помилку шлюзу від помилки ПК |
| Протокол | сервер не підтримує параметри, сеанс зайнятий іншим користувачем | загальна причина + код FreeRDP у «Деталях» |
| Локальні ресурси | немає дозволу на мікрофон, папка видалена | сеанс продовжується без ресурсу, показується підказка |
| Дані | бекап з новішої версії, пошкоджений файл | зрозуміла відмова без змін у поточних даних |

**Журнал.** Кожен запис: час, ОС, версія застосунку, назва ПК, етап, код помилки. Паролі, ключі, токени й вміст буфера обміну не логуються ніколи. Журнал зберігає останні 7 днів і копіюється однією кнопкою. Телеметрії немає: нічого не відправляється з пристрою.

## Особливості платформ

Код інтерфейсу спільний, а відрізняється збірка нативних бібліотек, спосіб поширення й кілька системних деталей. Усі чотири версії збираються в GitHub Actions.

|  | Windows | Linux | macOS | Android |
| --- | --- | --- | --- | --- |
| Збірка FreeRDP | vcpkg + MSVC | CMake, статично в застосунок | CMake, universal (Intel + Apple Silicon) | Android NDK, arm64-v8a і x86\_64 |
| Збірка Go-модулів | c-shared .dll | c-shared .so | c-shared .dylib | c-shared .so через NDK |
| Поширення | інсталятор і портативний .zip | AppImage, пізніше Flatpak | .dmg | .apk, пізніше Google Play |
| Підпис | необов'язковий; без нього попередження SmartScreen | не потрібен | для запуску без попереджень потрібні підпис і нотаризація (платний акаунт Apple Developer) | власний ключ підпису, зберігати в секретах GitHub |

**Windows**

- Перехоплення Win та Alt+Tab у повноекранному режимі — низькорівневий хук клавіатури, активний лише коли вікно сеансу в фокусі.
- Імпорт збережених підключень із першої версії (data.json) при першому запуску.

**Linux**

- Підтримка X11 і Wayland. На Wayland перехоплення системних поєднань клавіш може бути обмежене композитором.
- Резервне сховище секретів з головним паролем, якщо немає libsecret.

**macOS**

- Без підпису застосунок відкривається через «Системні налаштування → Конфіденційність і безпека → Все одно відкрити». Для власного використання цього достатньо.
- Клавіша Cmd мапиться на Ctrl або Win — вибір у налаштуваннях.
- Для перехоплення системних поєднань потрібен дозвіл «Універсальний доступ»; застосунок просить його тільки тоді, коли користувач це ввімкне.

**Android**

- Сеанс у фоні тримається службою переднього плану з сповіщенням «Активних сеансів: N», інакше система розірве з'єднання.
- Вбудовані тунелі працюють без VpnService, тому не конфліктують з іншим VPN на телефоні.
- Підтримка фізичної клавіатури й миші (Bluetooth, USB-OTG) та режиму DeX / робочого столу.
- У значки застосунку — ярлики до частих ПК (довге натискання на іконку).

## Тест-план

Усі перевірки проходять на кожній з 4 ОС. Те, що не потребує реального сервера, запускається автоматично в GitHub Actions для кожної зміни.

| ID | Перевірка | Очікуваний результат | Авто |
| --- | --- | --- | --- |
| T-01 | ПК зі стандартним і нестандартним портом, IPv4, IPv6, DNS-ім'я | збережено, порт використано правильно | так |
| T-02 | ПК без пароля | пароль запитується при підключенні | ні |
| T-03 | Один акаунт у двох ПК, зміна пароля | обидва ПК використовують новий пароль; у журналі пароля немає | так |
| T-04 | Два акаунти на одному ПК, два сеанси одночасно | сеанси незалежні | ні |
| T-05 | Вкладені групи, переміщення, спроба створити цикл | цикл заблоковано | так |
| T-06 | Видалення групи, акаунта чи тунелю, якими користуються ПК | запит із списком ПК; жодного падіння потім | так |
| T-07 | 5000 ПК у списку | відкриття й пошук швидше 0,5 с | так |
| T-08 | Втрата мережі на 10 с і перехід Wi-Fi → мобільний | сеанс перепідключається сам, UI не зависає | ні |
| T-09 | Невірний пароль | одна спроба, жодних автоповторів | ні |
| T-10 | Новий і змінений сертифікат сервера | запит / червоне попередження, жодного тихого обходу | ні |
| T-11 | Підключення через RD Gateway | сеанс йде через шлюз; помилки шлюзу відрізняються | ні |
| T-12 | ПК з білим списком через вбудований WireGuard, без прав адміністратора | підключено; системний трафік пристрою не змінився | частково\* |
| T-13 | Два різні тунелі одночасно + системний VPN увімкнений | усе працює разом | ні |
| T-14 | Повний бекап на Windows → відновлення на Android і Linux | все на місці, паролі й ключі працюють | так |
| T-15 | Бекап із невірним паролем, пошкоджений, з новішої версії | зрозуміла відмова, дані не змінені | так |
| T-16 | Експорт для передачі | у файлі немає жодного секрету | так |
| T-17 | Вимкнення процесу під час збереження | база ціла | так |
| T-18 | Буфер обміну: текст і картинка в обидва боки, кирилиця | вставляється без спотворень | ні |
| T-19 | Немає дозволу ОС на мікрофон чи файли | пояснення, сеанс працює далі | ні |
| T-20 | Сеанс на Android 1 годину в фоні | не розірвано | ні |

\* Тунель і переадресацію можна перевіряти автоматично з тестовим WireGuard-сервером у контейнері GitHub Actions; сам RDP-сеанс перевіряється вручну.

## Етапи робіт і критерії готовності

Робота йде сімома етапами, кожен закінчується робочою збіркою, яку можна перевірити. Найбільший ризик — збірка нативних бібліотек на етапах 2 і 5.

1. **Каркас Flutter.** Моделі, сховище, список і редагування ПК, акаунти, профілі маршрутів, бекап; збірка під 4 ОС у GitHub Actions.
   - Готово, коли: бекап, створений на Windows, відновлюється на Android із тими самими паролями.
2. **Процес `mhrd-session` над FreeRDP і перше підключення** (спершу Windows).
   - Готово, коли: підключення до Windows Pro з NLA, запит на довіру до сертифіката, картинка, клавіатура й миша працюють; примусове завершення `mhrd-session` показує Failed, а застосунок працює далі.
3. **Екран сеансу.** Вкладки, повний екран, зміна розміру, перепідключення.
   - Готово, коли: два сеанси до одного ПК різними акаунтами працюють одночасно; після втрати Wi-Fi на 10 с сеанс перепідключається сам.
4. **Вбудований WireGuard.**
   - Готово, коли: ПК, доступний лише з адреси WG-сервера, підключається без прав адміністратора; два профілі працюють одночасно.
5. **Android.** Збірка FreeRDP і wireguard-go через NDK, сенсорне керування, фоновий сеанс.
   - Готово, коли: сеанс через WireGuard працює при ввімкненому іншому VPN і не рветься за 10 хв у фоні.
6. **Проксі, RD Gateway, буфер обміну, папки, звук, мікрофон, Wake-on-LAN.**
   - Готово, коли: кожен маршрут перевірений на реальному сервері; текст і картинки копіюються в обидва боки.
7. ~~**Додатковий тунель:** Tailscale/Headscale~~ — скасовано (рішення власника, 2026-10-31): системна програма Tailscale разом із маршрутом «напряму» дає той самий результат.

**Ліцензія:** MHRD — безкоштовний застосунок із відкритим кодом під AGPLv3, публічний репозиторій на GitHub. У коді, назвах пакетів і файлів використовується лише абревіатура `mhrd`, щоб розшифровку назви можна було змінити перед публікацією в магазинах.
